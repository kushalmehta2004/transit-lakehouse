Stop 1 · Ingestion

Live feed into Kafka

A Python poller fetches MBTA's GTFS-realtime protobuf feeds every 15 seconds (vehicle positions and trip predictions, no API key needed). It validates each record, stamps event_time and ingest_time, and produces JSON to Redpanda, a Kafka-compatible broker. Messages are keyed by route so each route stays in order. Anything it can't fetch, decode or validate goes to a dead-letter topic with the error attached.

Try it

  • Open the Kafka console at localhost:8080 → Topics → vehicle_positions.raw → Messages.
  • Follow the poller's log: docker logs -f poller. Each poll prints a line like 538 entities -> 443 produced, 95 unchanged, 0 invalid.
  • See its metrics at localhost:8000/metrics: gtfs_events_produced_total, poll latency, DLQ counts.
Stop 2 · Spark Structured Streaming

Bronze: exactly what arrived

A Spark streaming job reads both topics every 10 seconds and lands them, untransformed, into Apache Iceberg tables on MinIO (S3-compatible storage). Each row keeps its Kafka partition and offset, which is how exactly-once delivery was proven: after a kill -9, there were zero duplicate offsets. A Postgres-backed Iceberg catalog gives safe concurrent commits.

Try it

docker compose exec spark python sql.py "SELECT count(*) FROM bronze.vehicle_positions"
docker compose exec spark python sql.py "SELECT committed_at, summary['added-records'] FROM bronze.vehicle_positions.snapshots ORDER BY committed_at DESC LIMIT 5"
  • Spark UI at localhost:4040 → Structured Streaming. MinIO at localhost:9001 (minioadmin / minioadmin).
Stop 3 · Stream-static join + watermark

Silver: a delay for every stop

MBTA publishes only predictions. When a bus passes a stop, that stop disappears from the feed. So the silver job records the last prediction made before the stop vanished as the observed arrival. It joins that to the timetable (broadcast, filtered to the trips running that day, with correct handling of times like 25:10:00) and computes delay_seconds.

What happens to an event that arrives 20 minutes late?

A 15-minute event-time watermark holds each passed stop until no older update can still arrive, and only then writes it. Anything less than 15 minutes late still counts. Anything later is dropped from silver and counted, but it stays in bronze for backfill. Replaying real data with chunks reversed produced identical output, row for row. The cost is that silver lands about 16 minutes after the bus passes, which is the right trade-off for a historical question.

Checked against GPS

Of 14,394 stop visits where the vehicle's GPS reported STOPPED_AT that stop, the median difference was 6 s and 99.6% were within 60 s.

Try it

docker compose exec spark python sql.py "SELECT route_id, stop_id, scheduled_time, observed_time, delay_seconds FROM silver.stop_delays ORDER BY processed_time DESC LIMIT 10"
docker compose run --rm --no-deps spark python tests/replay_reorder.py   # the reorder + late-data test (~8 min)
  • docker logs -f spark-silver prints the watermark, state size and late-dropped count for each batch.
Stop 4 · dbt

Gold: the analytics tables

dbt connects through a Spark Thrift (JDBC) server and builds the gold layer. route_lateness_by_hour computes average, median and p90 delay per route, per day, per hour; it's incremental and overwrites only the days it reprocesses. chronically_late_routes rolls that up over seven days, and dim_routes adds names and modes. The lineage graph shows silver flowing into gold.

Try it

docker compose run --rm dbt dbt build              # 3 models + 24 tests
docker compose run --rm dbt dbt docs generate
docker compose run --rm -p 8085:8085 dbt dbt docs serve --host 0.0.0.0 --port 8085 --no-browser
  • Open localhost:8085 and click the graph icon at the bottom right for lineage.
Stop 5 · dbt tests + Great Expectations

39 quality gates

There are 24 dbt tests (non-null keys, one row per stop visit, route relationships, accepted values, and a custom delay_in_plausible_range) and a 15-expectation Great Expectations suite, which includes timestamp-ordering checks. Any failure turns the pipeline red. The gates caught two real bugs before they reached analytics: a stop counted twice after a trip vanished and came back hours later, and a deleted bad row whose aggregate lingered in gold.

Prove the gates work

docker compose run --rm dbt python /work/quality/bad_row_drill.py

This injects a stop visit with a 10-hour delay, then runs dbt and Great Expectations. Both must fail. Then it deletes the row, and both must pass again.

Stop 6 · Orchestration

Airflow runs it every 15 minutes

The pipeline DAG runs dbt_run → dbt_test → ge_checkpoint → mark_refresh. An alert_on_failure task runs only if something failed, and it turns the run red. A second DAG compacts the streaming tables hourly; it brought bronze from about 1,050 small files per table down to a handful. Airflow runs as a single container to keep the laptop footprint small.

Try it

  • Open localhost:8081 (admin / admin) → transit_lakehouse_pipeline → ▶ to trigger a run, then click any task to read its log.
Stop 7 · Prometheus + Grafana

See the whole pipeline at a glance

Prometheus scrapes the poller, all three Spark apps, Airflow (through StatsD), Redpanda, and a small custom exporter. The exporter measures what no single service can: Kafka consumer lag (from Spark's checkpoint offsets), DLQ depth, ingest-to-lakehouse latency, and data freshness. The Grafana dashboard asks one question per row.

Try it

  • Grafana at localhost:3000 opens on this dashboard. Prometheus alerts are at localhost:9090/alerts.
  • Reading a slowdown: if events/sec drops to 0 while freshness climbs and lag stays at 0, the source stopped. If events/sec is normal and lag climbs, Spark is behind.
Stop 8 · Failure drills

Break it, watch it, fix it

Run the drills yourself

docker compose stop poller     # watch Grafana ~8 min: Bronze lag climbs, alert fires

Stop 9 · Load, recovery, partitioning

Measured numbers

scripts/replay.py replays real Kafka history at rising rates until the pipeline falls behind. At 5k events/s the original bronze job broke, because a coalesce(1) made it run on one core out of twelve. Restoring one task per Kafka partition gave about 4× the throughput, at the same latency.

2k → 10k ev/ssustained throughput, before → after the fix
5.0 s / 9.9 sp50 / p99 ingest → bronze, unchanged at 10k ev/s
32 sbronze catch-up after 5 min down (40k-message backlog)
101 ssilver catch-up after 5 min down
1.9× fasterone route over 7 days with Iceberg partitioning (51 MB → 4 MB read)
11% slowerone route over full history: the over-partitioning trade-off

Reproduce

  • The full method, raw data and commands are in scripts/results/phase6_perf.md. Expect the load test to keep the laptop busy for about 20 minutes.
Stop 10 · Kubernetes (kind)

Deployed once to Kubernetes

The core pipeline (Kafka, MinIO, Postgres, the poller, and three Spark jobs) runs on a local kind cluster. Every pod has readiness and liveness probes, and the streaming jobs use Recreate rollouts so two writers never share a checkpoint. The autoscaler sits on the stateless SQL server. Two pollers would duplicate events, and two streaming jobs would corrupt their checkpoint.

Last stop

Run it yourself

You need Docker Desktop with about 12 GB of memory for containers. The first build takes 20–30 minutes; after that, startup takes a couple of minutes. MBTA's feed needs no API key.

First start

git clone https://github.com/kushalmehta2004/transit-lakehouse.git
cd transit-lakehouse
cp .env.example .env
docker compose build
docker compose --profile tools build dbt
docker compose up -d
docker compose ps        # wait for (healthy)

What appears when

  • ~10 s: live messages in Kafka
  • ~1 min: rows in bronze
  • ~16–20 min: rows in silver (the watermark)
  • next quarter hour: gold tables and quality gates via Airflow
  • Stop with docker compose stop; resume with docker compose up -d
